# Sources

No skill loads this file. It records where each practice in `frie-core` comes from, so a rule can be checked against its source when it is questioned. A rule listed under Preferences is Brandon's own choice and needs no source.

The "Stated in" column gives the file and section. `SKILL.md`, `architecture.md`, and `testing.md` are the three files of the `engineering-patterns` skill.

## Stricter than mainstream practice

Brandon chose the stricter form of each rule here on purpose, because the reader is a code agent. The note gives the mainstream position and then the strongest dissent. Each source was read on 2026-11-26 unless the note says otherwise.

| Rule | Stated in | Source | Note |
|---|---|---|---|
| Existing code that disagrees with the skills is drift, never precedent | `SKILL.md`, Precedence | Google Engineering Practices, "What to look for in a code review": https://google.github.io/eng-practices/review/reviewer/looking-for.html | Google treats the style guide as the absolute authority and applies consistency with existing code only where no rule covers the point. PEP 8 says consistency within a project is more important, and Google allows a deviation when local inconsistency would confuse readers. |
| Anything callable has a verb-phrase name | `SKILL.md`, Naming | Microsoft, Names of Type Members: https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/names-of-type-members | The .NET guidelines give methods verb or verb-phrase names and properties noun or adjective names. The Google Java Style Guide says method names are only typically verbs. |
| Three parameters at most | `SKILL.md`, Signatures | Refactoring.Guru, Long Parameter List: https://refactoring.guru/smells/long-parameter-list | A parameter list counts as a design problem at more than three or four parameters. Checkstyle's default limit is seven, and the page warns against dropping parameters when that would create an unwanted dependency between classes. |
| Never an operator that silences the null checker without a runtime check | `SKILL.md`, Values and absence | typescript-eslint, no-non-null-assertion: https://typescript-eslint.io/rules/no-non-null-assertion/ | The strict typescript-eslint configuration treats an assertion as a sign that code is not fully type-safe. Microsoft documents `!` as legitimate when the author knows an expression cannot be null and the compiler does not. |
| No empty catch blocks, and a deliberate swallow logs at trace level or above | `SKILL.md`, Errors | Google Java Style Guide: https://google.github.io/styleguide/javaguide.html | Google says it is very rarely correct to do nothing in response to a caught exception. Google permits a justified empty block with a comment. |
| A wrong comment is deleted and never corrected, unless it is a required comment | `SKILL.md`, Comments and documentation | PEP 8: https://peps.python.org/pep-0008/ | PEP 8 says comments that contradict the code are worse than no comments. The same sentence asks authors to keep comments current, which means correcting them. |
| Never suppress a warning, by any route | `SKILL.md`, Suppressions | Microsoft, Suppress code analysis warnings: https://learn.microsoft.com/en-us/dotnet/fundamentals/code-analysis/suppress-warnings | Microsoft's rule pages say "Do not suppress" for many rules and show a `Justification` on `SuppressMessage`. Microsoft also documents rules as safe to suppress in stated cases, and typescript-eslint recommends targeted disable comments. |
| A subsystem's storage is internal, and no other subsystem reads it even through a query or a view | `architecture.md`, Subsystems | Martin Fowler, "Integration Database": https://martinfowler.com/bliki/IntegrationDatabase.html | A shared database couples applications tightly, so applications should avoid one. Fowler notes that a shared database saves an integration layer, and his CQRS page accepts a reporting database that combines data from several places. |
| Every type has exactly one owning subsystem, and no `Common`, `Shared`, or `Utils` folder exists | `architecture.md`, Subsystems | Martin Fowler, "Bounded Context": https://martinfowler.com/bliki/BoundedContext.html | Each bounded context holds its own model of a concept. Eric Evans's shared kernel lets two contexts share a deliberately chosen subset of the model. |
| The folder tree is the subsystem tree, and a folder's name states a responsibility and never a kind of type | `architecture.md`, Code layout | Simon Brown, "Modular monolith": https://simonbrown.je/modular-monolith | Packaging by layer does not show what a system is about, so domain-oriented modules are preferred at the top level. Brown calls pure package-by-layer and pure package-by-feature both suboptimal and says enforcement matters more than folder names. |
| When any arm of a dispatch is not trivial, every arm becomes its own type | `SKILL.md`, Constructs | John Ousterhout, CS 190 lecture notes, Modular Design: https://web.stanford.edu/~ouster/cgi-bin/cs190-winter18/lecture.php?topic=modularDesign | Replace Conditional with Polymorphism is a standard refactoring when the arms hold behavior. Ousterhout says small classes taken to the extreme add interface cost and little depth. The page was read for the dissent only. |
| Reason about growth before measuring, and reject the listed shapes without measurement | `architecture.md`, Performance | Wikipedia, "Program optimization": https://en.wikipedia.org/wiki/Program_optimization | The choice of algorithm and data structure is the most powerful optimization and is costly to change late. Donald Knuth says to forget small efficiencies 97% of the time, and intuition about bottlenecks is often wrong. |
| The red run is executed and its failure output shown before any implementation, on every cycle | `testing.md`, TDD | Kent Beck, "Canon TDD": https://newsletter.kentbeck.com/p/canon-tdd | Canon TDD presumes a failing test and does not require showing the failure. No dissent of substance exists, and the cost is run time. |
| The compile failure is the first red, and each missing type is a stub whose members fail loudly | `testing.md`, TDD | Kent Beck, "Canon TDD": https://newsletter.kentbeck.com/p/canon-tdd | Beck counts a compile failure as red in *Test-Driven Development: By Example*, and stubs that throw are a common convention that Canon TDD does not include. | Never assert on text written for a human reader or on a serialized form | `testing.md`, How to assert | *Software Engineering at Google*, chapter 12: https://abseil.io/resources/swe-book/html/ch12.html | Mainstream guidance agrees that message text and rendered output make brittle tests, and allows them case by case. ## Contested in the field

Published authors disagree about each of these. The note gives the position that supports the rule and then the position against it. Each source was read on 2026-11-26.

| Rule | Stated in | Source | Note |
|---|---|---|---|

Ousterhout calls comments essential and irreplaceable, because much important information cannot be expressed in code. |
| No redundant null guards | `SKILL.md`, Values and absence | Microsoft, Parameter Design: https://learn.microsoft.com/en-us/dotnet/standard/design-guidelines/parameter-design | With nullable types and a checker, a guard on a value proven non-null adds nothing. | An expected failure is a `Result`, and an exception means a bug or an infrastructure failure | `SKILL.md`, Errors and Results | Scott Wlaschin, "Against Railway-Oriented Programming": https://fsharpforfunandprofit.com/posts/against-railway-oriented-programming/. The .NET Framework Design Guidelines say "DO NOT return error codes" and report every execution failure by exception. |

| Every behavior a unit test can reach is written test first | `SKILL.md`, Testing, and `testing.md`, TDD | Kent Beck, "Canon TDD": https://newsletter.kentbeck.com/p/canon-tdd | Beck's Canon TDD writes one failing test and then changes the system so it passes. | Records stay dumb, and rules that depend on a previous state live in a service | `architecture.md`, State, and `SKILL.md`, Constructs | Martin Fowler, "Anemic Domain Model": https://martinfowler.com/bliki/AnemicDomainModel.html | Functional-first authors such as Wlaschin keep data and behavior apart. | Tests for existing code take expectations from what the feature is for, never from a value the code produced | `testing.md`, TDD | Michael Feathers, "Characterization Testing": https://michaelfeathers.silvrback.com/characterization-testing | Beck lists pasting actual computed values into expected values as a mistake. | A test name has three parts, with a mandatory condition | `testing.md`, Naming | Roy Osherove, "Naming standards for unit tests": https://osherove.com/blog/2005/4/3/naming-standards-for-unit-tests.html. | Every value a test builds comes from a seeded Faker generator | `testing.md`, Test data | Mark Seemann, "Constrained Non-Determinism": https://blog.ploeh.dk/2009/03/05/ConstrainedNon-Determinism/.
